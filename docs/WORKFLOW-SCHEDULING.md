# Conditional and scheduled workflows

Workflow templates can attach `condition: {step: 0, operator: "has_evidence"}` (or `"no_evidence"`) to a non-approval step. `step` is the zero-based index of an earlier search or review step. The builder presents numbered source steps. Forward references, non-evidence sources and conditional approval steps are rejected by the API. Reordering steps requires reviewing those references before saving.

A branch reads the earlier output's persisted citation count. `has_evidence` requires at least one recorded citation; `no_evidence` requires exactly zero. This describes retrieval evidence, not the legal presence or absence of a clause. If the referenced step was skipped or its count is unknown, the dependent step is skipped rather than treating unknown as zero. Every skip records its condition and reason in the run timeline. Completed outputs and branch decisions survive restart. Approval steps always pause and retain independent-review and distinct-reviewer requirements.

Use **Schedule** beside a workflow template to save a recurring run. Choose an interval of at least 60 minutes and explicitly enable execution. Scheduling can invoke configured model generation and consume provider usage. Schedules are limited to 50 per workspace and share the existing limit of 20 active workflow runs. By default schedules are saved disabled. The first occurrence is one interval after enabling; re-enabling restarts that interval. Disabled schedules do not cancel an existing run: use that run's Cancel action separately.

Each occurrence snapshots the latest template and the current active document versions unless explicit document IDs were supplied to the API. A scheduled run retains the original schedule creator as actor. Before creating a run, and again before each workflow step, the server rechecks current membership and matter grants. A missing source, removed permission, disabled member, invalid template or run limit pauses the schedule; resolve it and explicitly enable again.

Schedules execute only while Counsel is running. There is no external operating-system scheduler. Run creation and the next due timestamp commit together in SQLite, so restart cannot create a duplicate occurrence. Missed intervals coalesce into one occurrence. If that schedule's previous run is queued, running or awaiting approval, the occurrence is skipped and recorded in schedule status; no second run starts. New occurrences do not inherit approval from any previous run.

Routes: `GET/POST /api/workflow-schedules`, `PATCH /api/workflow-schedules/:id` with `{enabled:boolean}`. Creation accepts `{templateId, run:{matterId,input,documentIds?}, intervalMinutes, enabled}`. The creator or workspace owner can enable/disable a schedule with current matter access. Template updates use version checks; schedule toggles apply the requested enabled state. Listing is filtered by current matter access and omits stored run instructions.

Verification: `node --test test/workflows.test.js test/workflow-schedules.test.js` covers actual authorized route execution, backward condition validation, both evidence branches, mandatory approval pauses, durable database close/reopen, disabled scheduling, repeated occurrences, overlap prevention and membership revocation. Native clock/operating-system wakeups and multi-process worker coordination are not claimed; operate one Counsel process per SQLite database.
